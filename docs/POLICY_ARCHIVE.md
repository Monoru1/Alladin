# Dossiers et archive de politique — OBSERVE/PAPER

`PolicyArchive` conserve dans un fichier SQLite distinct du journal de trading les documents reçus, batches économiques validés, dossiers par binding/programme/phase et révocations. Chaque contenu est sérialisé canoniquement et hashé. Une identité existante ne peut pas être réécrite ; une réimportation identique est idempotente. Les connexions sont fermées et les append utilisent des transactions SQLite. Ce stockage n'est ni une authentification des éditeurs ni un coffre de secrets ; une réécriture malveillante complète de la base n'est pas empêchée.

Un batch exige le document brut préalablement archivé, avec même source, URL, heure de réception et SHA-256 de contenu. Cette liaison prouve la traçabilité locale, pas la justesse du parseur ni les affirmations de l'éditeur. Le replay filtre également l'heure locale d'archivage : importer aujourd'hui une réception datée d'hier ne la rend pas visible rétroactivement dans les simulations. Les dates futures et horloges naïves sont rejetées. Les valeurs et horizons restent validés par les contrats d'ingestion.

`PolicyDossier` lie le profil à un AccountBinding complet (workspace/broker/référence masquée/serveur/type/fingerprint éventuel), programme, phase, preuve de document, référence de revue et expiration. États : DRAFT et SIMULATION_ONLY. Aucun état d'admission financière ni mode DEMO/LIVE n'existe dans ce contrat. DOCUMENT_REFERENCE est une référence fournie, pas une validation officielle automatique. SYNTHETIC désigne des fixtures. Dossiers périmés, révoqués, ambigus, mauvais binding/programme/phase/mode : indisponibles. La version la plus récente connue ne permet aucun fallback à une ancienne version plus permissive. La revue des contrats et l'admission réelle restent à réaliser indépendamment.

`CoveragePlan` énumère les sources requises pour chaque symbole, la version/source de cette configuration et les horizons minimum (120 s passées, 900 s futures, extensibles). Chaque composant doit être reçu, frais, explicitement déclaré complet, hashé et couvrir l'horizon demandé. Une source inconnue, manquante, périmée, partielle ou sans horizon rend le composite incomplet. Les sources BLS/BEA publiques connues ne peuvent pas être marquées complètes dans l'archive. Ajouter leurs événements ne complète donc pas automatiquement un calendrier mondial.

Les identifiants d'événements sont qualifiés par source pour éviter les collisions de révisions. Le composite conserve les hashes des batches et les gaps. Une révision reçue après l'instant du replay n'est pas utilisée ; un refresh récent périmé n'est jamais remplacé opportunément par une ancienne version encore valide. La complétude déclarée d'une autre source reste une affirmation à vérifier, pas une garantie indépendante.

`ArchivedPolicyProvider` assemble un contexte sans réseau, sans lecture de compte et sans exécution. Il est explicitement injecté dans PolicyController/Components.engine ; mode et binding doivent correspondre. Les collecteurs de positions, état de drawdown, horaires, expositions, risque et groupes sont injectés par l'appelant. L'absence de données requises produit un refus/revue, jamais un zéro implicite autorisant une nouvelle exposition. Les preuves dossier/composite sont enregistrées dans policy.decision. Les ensembles et dates produisent des hashes stables entre processus et fuseaux.

Tests : persistence/restart/idempotence, hash de contenu, conflits d'identité, délais de collecte/archivage, révocation, expiration sans fallback, isolation de compte/phase, horizons, collisions inter-sources, calendriers partiels, modes incompatibles, gestion PAPER via MockBroker sans envoi broker. Aucun déploiement, source complète réelle ou admission contractuelle n'est activé.

Le sélecteur de phase peut être une chaîne ou une fonction explicitement injectée : un changement impose un dossier disponible pour cette nouvelle phase ; aucun fallback à la phase précédente. Ce sélecteur ne découvre pas le statut réel d’un compte financier.
